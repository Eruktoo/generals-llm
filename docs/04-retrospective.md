# Generals LLM — 项目复盘

## 1. 我们实际建成了什么

这个项目已经不是单纯的概念验证，而是一个可以跑起来的最小闭环：

- `engine/`：纯 Python 游戏引擎，负责地图、棋盘状态、移动、战斗、产兵、战争迷雾、排名和胜负判定。
- `agents/`：4 个 LLM agent，人格分别是赌徒、保守派、诡计者、疯子。每个 agent 接收自己的战争迷雾视角，输出 JSON 战略。
- `execution/`：执行层，把 LLM 的高层战略翻译成具体 `Move`。
- `web/`：HTTP 服务和单页 Canvas 前端，后台预计算回合，前端按轮播放。

整体架构是对的：引擎不依赖 LLM；agent 只看自己的 `BoardView`；执行层隔离了“语言模型决策”和“合法移动生成”；前端只消费服务端状态。

但当前实现离“好玩的策略游戏”还有明显距离。

### `engine/`

能工作的部分：

- `Board.generate_map()` 能生成 12x12 地图、山、城市、四个将军。
- `Game.step()` 能推进半回合，phase 0 产兵，phase 1 只移动。
- 移动、合兵、攻击、中立城市占领、将军被攻陷后吞并玩家都已实现。
- `get_player_view()` 有战争迷雾，每个玩家只看到自己部队和城市周边。
- `RandomBot` 和 demo 能用于基本验证。

问题：

- 地图生成很粗糙。起始点固定在角落附近，山和城市随机放置，没有连通性、距离、公平性检查。
- generals.io 的节奏被大幅简化。没有真正的“每回合所有格增长”细节调优，也没有路线队列、连续拖动、取消指令等关键体验。
- `Board.adjacent4()` 包含自身，这对视野是合理的，但名字容易误导。
- `Game.execute_moves()` 对移动排序有问题。注释和实现不一致，而且攻击将军被设为最低优先级，这可能让致命攻击被其他移动影响。
- 同一批 moves 被连续执行 6 个 half-turn，这不是“持续计划”，更像是把一个静态命令重复提交 6 次。来源格第一步后常常只剩 1 兵，后续移动失效；如果来源是将军，phase 0 产兵后又可能重复抽兵。

### `agents/`

能工作的部分：

- prompt 会包含人格、当前回合、阶段、存活敌人、总兵力、格数、城市、将军位置、产兵、可见地图和排名。
- DeepSeek API 调用失败或没有 key 时，会使用 `simulate_llm()` 作为 fallback。
- `parse_response()` 能从纯 JSON 或夹杂文本中提取 JSON，并做字段校验。
- 输出被限制在 stance、objectives、direct_orders、constraints 这几个可执行字段里。

问题：

- prompt 要求“高层战略”，但缺少关键战术摘要：边境、威胁、可进攻目标、路径、上轮执行结果、失败原因。
- `history` 只是存起来，没有进入下一轮 prompt。agent 没有真正的连续记忆。
- 人格差异主要来自系统提示和默认约束，不是从策略能力上体现。实际行为很容易收敛成“扩张/防守/增援”的模板。
- 解析失败后直接 fallback 到模拟策略，能保证不中断，但会掩盖真实 LLM 输出质量问题。
- `simulate_llm()` 本身已经是一个规则 bot。很多时候即使不调用 LLM，项目也能继续跑，这削弱了 LLM 的必要性。

### `execution/`

能工作的部分：

- 支持 `expand_region`、`reinforce_region`、`attack_position`、`defend_region` 和 `direct_orders`。
- 会按 priority 排序 objective。
- 会避免重复使用同一 source。
- 会校验边界、山、迷雾障碍、来源兵力、将军/城市最小驻军、最大投入比例。
- 约束太严格时会放宽驻军要求，避免完全卡死。

问题：

- 执行层仍然太弱。它只做一步移动，不做路径规划、兵力集结、目标持续追踪、局部战斗评估。
- `expand_region` 只扩可见中立或 fog，不会主动设计探索路线。
- `reinforce_region` 从区域外找兵往弱格走，但只走一步，不保证下一轮还能继续。
- `attack_position` 只是朝目标走一步，最多 1 或 3 个 stack，没有判断兵力是否足够、路径是否可达、目标是否仍然可见。
- `defend_region` 只是把深处兵力往边界送，可能制造拥堵或抽空后方。
- `max_commitment_percent` 用的是“可见己方总兵力”，在迷雾视角下这是自己的全部可见兵力，基本等同己方兵力；但它限制的是单个 move 的 moving army，不是整轮总投入。
- 0-move 是真实问题。开局将军兵力为 0，保守 agent 又可能防御优先、不向 fog 走，导致多轮空转。

### `web/`

能工作的部分：

- `web/server.py` 启动后会后台预计算游戏。
- 每轮并行调用 4 个 agent，再将结果交给执行器。
- 前端可以查看当前状态、下一轮、跳转、重置。
- Canvas 能显示格子、山、城市、将军、兵力、排名和日志。

问题：

- 前端展示的是全图状态，不是某个玩家视角；这适合观战，但削弱了“每个 agent 有私有信息”的可解释性。
- 日志只显示 plan、reasoning、move 数、目标数和前三个 move。看不出哪些指令被拒绝、为什么拒绝、哪些目标失败。
- 后台会持续预计算整局。用户看到的是 replay，不是真正实时等待 agent 决策。
- 没有 prompt、raw response、parsed strategy、executed moves、board diff 的调试界面。现在很难判断一次烂操作到底是谁的问题：模型、prompt、parser、executor 还是 engine。

## 2. LLM 分工是否正确

目前的分工方向是正确的：LLM 做 stance、目标、区域、少量直接命令；执行层做具体合法移动。

让 LLM 直接输出每个格子的移动不现实。棋盘一旦有 20 个以上己方格子，模型就会遗漏、重复、过期、非法。它擅长的是判断“我要稳住将军、扩西北、准备打这个城市”，不是每半回合精确调度几十个格子。

但是当前执行层还没有强到足以承担战术细节，所以系统处在中间尴尬区：

- LLM 输出的目标太粗，执行层无法把它变成有效战役。
- direct order 太具体，但 LLM 对当前局面细节又不够可靠。
- 每 6 个 half-turn 才重新决策，计划经常过期。
- 同一批 moves 被重复执行 6 次，不是“执行计划”，而是“重复提交旧动作”。

### 主要失败模式

**约束阻塞**

保守派默认 `min_general_garrison=30`、`max_commitment_percent=30`，开局兵少时很容易什么都不能动。虽然执行层会把驻军放宽到 1，但 `avoid_fog=True` 时仍然会阻塞探索。结果是防御姿态经常变成停滞。

**0-move rounds**

快速运行 fallback 逻辑时，第一轮 4 个玩家都是 0 moves。之后保守或防御姿态仍可能多轮 0 moves。原因包括：

- 开局将军兵力不足。
- 防御目标没有可移动深处兵力。
- 增援目标找不到合适弱格或路径。
- 避免迷雾导致没有合法目的地。
- objective 区域选得太抽象，里面没有可执行 frontier。

**prompt 格式和 schema mismatch**

prompt 给了 JSON 示例，但模型可能输出额外解释、字段名偏差、自然语言区域、错误坐标。代码有 JSON 提取和校验，但失败会悄悄 fallback。这样比赛不会崩，但调试会失真：你以为是 LLM 在玩，实际可能是模拟规则在玩。

**计划过期**

一个策略只看当前视野，却被执行 6 个 half-turn。敌人移动、城市被占、路径被堵、兵力变化后，原始 move 仍被反复尝试。越到中后期，这个问题越严重。

**执行器没有战役记忆**

上一轮说“攻击某城市”，下一轮不会知道这次攻击推进到哪里、失败在哪里、是否应该继续。LLM 的 `history` 也没有回灌 prompt。战略没有连续性。

## 3. 优点和根本问题

### 真正好的地方

第一，分层清楚。`engine`、`agents`、`execution`、`web` 的边界基本正确。这让后续替换模型、加强执行器、改前端都比较容易。

第二，私有视野是真的。每个 agent 通过 `get_player_view()` 拿到自己的雾中地图，不是一个全知模型假装不知道。这是多 agent 实验最重要的基础。

第三，LLM 输出不是直接信任。解析、校验、约束、fallback 都有，系统不会因为一个坏 JSON 直接停摆。

第四，成本低。DeepSeek 调用便宜，4 路并行也能把单轮等待压住。作为实验，成本不是主要瓶颈。

第五，观战闭环已经有了。虽然前端简陋，但能看到棋盘、排名、日志和回放，这比纯命令行更容易调试行为。

### 根本破损的地方

第一，游戏本身还不够有策略密度。12x12、随机山城、四角出生、单一兵力资源，导致大部分决策都是扩张、攒兵、撞边境。LLM 的语言能力没有太多发挥空间。

第二，执行层太局部。当前执行器没有真正的路径规划和兵力管理，所以高层战略经常落不到有效行动上。LLM 说“进攻”不等于军队真的能形成攻势。

第三，回合抽象有问题。每轮决策一次，然后重复同一批 moves 6 次，会产生很多假动作和失效动作。更合理的是：LLM 输出一个持续目标，执行器每个 half-turn 根据最新局面重新生成 moves。

第四，可解释性不足。现在只能看到“说了什么”和“出了几步”，看不到“为什么没动”。对 LLM 系统来说，失败解释比成功动画更重要。

第五，LLM 的差异性不够硬。人格 prompt 会影响文字和少量约束，但游戏机制没有给欺骗、谈判、长期承诺、隐蔽意图太多空间。四个 agent 很可能只是四个参数不同的规则 bot。

## 4. “多 agent” 是否产生了涌现行为

目前只能说：架构上具备多 agent 条件，但还没有充分产生多 agent 价值。

有价值的部分是信息隔离。每个 agent 只知道自己的视野，这会自然产生误判、探索、边境冲突和局部不对称。这个基础是真的。

但这不等于已经有明显涌现行为。当前游戏太简单，agent 之间没有通信、联盟、威胁、交易、虚张声势的可执行机制。所谓“赌徒”“诡计者”的差异主要体现在 prompt 文案和进攻/防守参数上，而不是复杂互动。

在 generals.io 风格的规则里，涌现主要来自：

- 同时行动造成的碰撞。
- 迷雾下的错误判断。
- 主力位置隐藏。
- 多线推进和偷将军。

这些机制项目里有一部分，但执行器还不够强，导致 agent 很难做出真正多线欺骗、诱敌深入、声东击西。游戏会更常表现为：各自扩张，接触后局部消耗，兵多者滚雪球。

所以结论是：多 agent 是正确方向，但当前玩法还太薄，执行能力也太弱，涌现行为尚未被充分释放。

## 5. 成本收益是否成立

假设一局约 400 次 DeepSeek 调用、5 分钟计算、约 0.03 美元，账面成本很低。真正的成本不是钱，而是延迟和复杂度。

现在的问题是：LLM 提供的增量价值不稳定。

它提供的价值：

- 每个玩家能有独立视角和人格。
- 日志里能产生可读的战略意图。
- 在不写大量策略代码的情况下，快速得到“看起来像指挥官”的决策。
- 后续可以扩展到解释、复盘、观众视角、人格化叙事。

它没有充分提供的价值：

- 当前规则下，强规则 bot 可能会打得更好、更快、更稳定。
- LLM 没有真正处理复杂外交、欺骗、谈判或长期计划。
- 执行层弱时，LLM 的好想法也落不下去。
- 执行层强到足够好时，LLM 又可能只剩“给规则 bot 调参数”。

以现在的状态，LLM 不足以证明自己比规则 bot 值得。0.03 美元不是问题，5 分钟也不是绝对问题；问题是观众是否能看出“这是 LLM 才能产生的策略”。目前多数时候看不出来。

如果目标是做一个强 bot，对 generals-like 游戏来说，规则/搜索/启发式会更好。如果目标是展示多 agent LLM，应该让规则更强调语言模型擅长的东西：不完全信息推理、承诺、欺骗、联盟、计划解释、风险偏好，而不是每轮格子移动。

## 6. 最重要的 3 个建议

### 1. 改掉“重复执行同一批 moves 6 次”

这是当前最应该修的架构问题。

LLM 每轮输出的是战略，不应该直接产出一批被重复使用的 `Move`。更合理的流程：

1. LLM 每 N 个 half-turn 输出一次 strategy。
2. strategy 保存为 agent 的当前意图。
3. 每个 half-turn，执行器基于最新 `BoardView` 和当前 strategy 重新生成 moves。
4. 如果局面剧烈变化，例如发现敌将、将军受威胁、主力被打穿，提前触发 LLM 重新决策。

这样可以保留低频 LLM 调用，又避免旧 move 反复失效。

### 2. 把执行层升级成真正的战术控制器

执行器至少需要：

- BFS/A* 路径规划，能绕山、绕已知障碍。
- 前线识别：中立前线、敌方前线、将军防区、城市目标。
- 兵力集结：把多个来源汇聚到 staging tile，而不是每个来源各走一步。
- 攻击评估：判断目标兵力、己方可投入兵力、路径风险、是否值得打。
- 防守评估：识别将军危险路径、敌方大 stack、边境缺口。
- 每个 objective 的执行结果：成功、部分成功、被阻塞、无合法移动、兵力不足。

没有这个，LLM 再聪明也只是写愿望清单。

### 3. 建立可观测性和基准 bot

现在缺少判断质量的仪表盘。应该增加：

- 每轮保存 prompt、raw response、parsed strategy、executor rejected reasons、executed moves、board diff。
- 日志显示 0-move 的具体原因，而不是只显示“空”。
- 写一个确定性 heuristic bot，作为 baseline。
- 跑批量对局，比较 LLM agent、fallback agent、random bot、heuristic bot 的胜率、平均回合、0-move 比例、非法/被拒指令比例、API 延迟。

如果 LLM 打不过一个简单 heuristic bot，就不要继续调人格 prompt；先改玩法或执行层。

## 总结

这个项目的工程分层是合理的，最小闭环也已经跑通。真正的问题不是“LLM 能不能接进来”，而是“接进来之后它是否做了有价值的事”。

目前答案偏负面：LLM 的战略输出还没有被执行层充分转化，游戏规则也没有给多 agent 语言智能足够舞台。它现在更像一个带人格日志的自动 generals-like 模拟器，而不是一个能稳定展示 LLM 多 agent 策略涌现的游戏。

下一步不要优先美化 prompt，也不要先扩地图。先修执行循环、战术执行器和可观测性。等系统能清楚解释“为什么这轮没动、为什么打这里、为什么输了”，再判断 LLM 是否真的值得留在核心循环里。
